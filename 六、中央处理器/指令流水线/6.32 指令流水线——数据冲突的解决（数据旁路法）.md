#### 为什么封死？——关键路径会变长

> **"尽管可以实现该功能，但 EX 功能段的关键路径延迟增大到了 MEM 功能段访存延迟加 EX 功能段的 ALU 延迟"**

这句话的含义是：

如果要在同一拍内完成"MEM 读出数据 → 旁路 → ALU 使用"，那么 **ALU 的输入就必须等访存的结果出来后才能开始运算**

这就导致 EX 段的**关键路径**（决定时钟周期长度的那条最长信号路径）从原来单纯的：

```
寄存器读出 → ALU 运算 → 输出结果
```

变成了：

```
寄存器读出 → ALU 运算(部分) → 等MEM访存完成 → 旁路数据送达 → ALU 运算(剩余)
```

也就是 **EX 段延迟 = ALU 延迟 + 访存延迟（两者串联）**

---

### 为什么关键路径变长是致命问题？

右侧第二条要点：

> **"指令流水线的频率取决于流水线中最慢的功能段（短板效应）。因此，对于图中所示的情况，会使流水线频率严重降低"**

流水线的时钟周期由**最慢的一段**决定。原本 5 段中每段延迟大致均衡：

```
IF ≈ ID ≈ EX ≈ MEM ≈ WB  →  时钟周期 = 任意一段的延迟
```

如果 EX 段吸收了访存延迟，变成：

```
EX' = EX + MEM  →  EX' 变成最慢的段
时钟周期 = EX' = EX + MEM  →  几乎是原来的两倍
```

频率直接**腰斩**，所有指令都跟着慢了一倍

### 和之前"时间差"解释的关系

两个角度说的是同一件事的**两面**：

|        角度         |                            说法                            |
| :---------------: | :------------------------------------------------------: |
|  **时间角度**（之前讲的）   |            ALU 在第4拍中段需要数据，但访存到第4拍末才出数据 → 赶不上             |
| **硬件延迟角度**（这张图讲的） | 如果非要让 ALU 等访存结果再运算，那 EX 段的关键路径 = ALU延迟 + 访存延迟 → 时钟周期被迫拉长 |

前者解释"为什么赶不上"，后者解释"即使你硬要赶，代价是什么"

---

#### 一句话总结

**不是物理上做不到这条旁路线，而是如果允许数据从 MEM 段直接旁路回 EX 段的 ALU，就会把"访存延迟 + ALU 延迟"叠加到同一条关键路径上**，使 EX 段成为整个流水线的瓶颈，**时钟频率严重降低**。所以工程上的选择是宁愿插入一个气泡（stall 一拍），也不愿意让全局降频
